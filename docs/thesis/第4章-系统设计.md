本章在上一章需求分析的基础上，给出系统的总体架构、数据库结构、功能模块划分与关键业务流程的设计方案。设计遵循两条主线：其一，以「from 账户减少、to 账户增加」的统一规则表达全部资金变动，使记账、导入、对账等操作共用一套余额更新逻辑；其二，将余额联动、冲销重算等账务写操作全部约束在数据库事务之内，保证任意操作下数据的一致性与可追溯性。

## 4.1 系统总体架构设计

系统采用前后端分离的单体架构。个人账务管理系统的并发规模有限、业务规则高度集中于服务端，将界面呈现与业务处理拆分为两个独立工程，既使前端可以专注于交互体验的迭代，也使后端接口可以被未来的移动端复用。

前端为基于 Vue 3 的单页应用，共包含登录注册、首页仪表盘、记一笔、流水管理、账户管理、分类管理、账单导入、统计报表与个人信息 10 个功能页面，界面组件采用 Element Plus，图表可视化采用 ECharts，全局状态与路由分别由 Pinia 和 Vue Router 承担。开发期由 Vite 开发服务器将 `/api` 请求代理转发至后端，避免浏览器跨域限制。

前后端之间通过 REST 风格接口以 JSON 格式通信，除注册与登录外的全部接口均要求携带 JWT Bearer Token，由后端拦截器统一完成身份认证。

后端基于 Spring Boot 构建，采用经典四层架构：Controller 层负责接收请求、参数校验与出参组装；Service 层承载业务规则，并以此层作为事务边界；Mapper 层经 MyBatis-Plus 完成数据访问，全部 SQL 均为参数化执行；Common 与 Config 包提供统一返回格式、全局异常处理、JWT 拦截与跨域配置等公共能力。数据层采用 MySQL 8，共 5 张数据表。系统总体架构如图 4.1 所示。

## 4.2 数据库设计

### 4.2.1 概念结构设计

系统涉及用户、账户、分类、交易记录与导入批次 5 个实体，均为 1:n 的联系：

- 用户与账户、分类、交易记录、导入批次之间均为「拥有」联系，全部数据按 user_id 严格隔离；
- 分类与交易记录之间为「标注」联系，一笔流水至多归属一个分类，未选择分类时 category_id 为空；
- 导入批次与交易记录之间为「包含」联系，一个批次汇总一次账单导入产生的全部流水；
- 账户与交易记录之间存在「转出 / 转入」两个方向的联系：一笔支出或转账以 from_account_id 记录资金流出的账户，一笔收入或转账以 to_account_id 记录资金流入的账户。

### 4.2.3 关键数据规则

在表结构之上，系统约定了四条贯穿全部模块的数据规则：

（1）**余额联动原子化**。账户余额一律通过 `UPDATE account SET balance = balance ± 金额` 的原子语句增减，业务代码不读取余额后再写回，避免了并发下的丢失更新；流水写入与余额更新处于同一事务，任一步失败整体回滚，二者同生共死。

（2）**负债账户余额为负**。欠款以负数存储，界面层以正数展示欠款金额。由此全部资金变动统一为「from 账户减、to 账户加」一条规则，还款、负债消费等场景无需任何特殊分支，净资产等于全部账户余额直接求和。

（3）**流水软删除，重复检测置于应用层**。流水删除仅置 is_deleted 标记并反向冲销余额，历史可追溯；重复检测不依赖数据库唯一约束，而是在应用层比对 is_deleted = 0 的同源记录与当前批次内记录。这一设计使批次撤销后同一账单文件可以重新导入，而历史行仍完整保留。

（4）**初始余额锁定，偏差走对账校正**。账户建账后初始余额不可修改，余额与实际不符时通过余额校正功能录入实际值，系统自动生成一条 source = reconcile 的差额校正流水。校正流水进入历史，可查询、可冲销，差额全程可追溯。

## 4.3 核心功能模块设计

系统划分为 6 个功能模块。用户模块提供注册、登录、修改密码与修改昵称，注册成功时为用户复制 39 个预置分类并创建默认现金账户；基础资料模块管理账户与分类两类基础数据，账户支持资产/负债两类与归档机制，余额校正（对账）亦归属本模块；记账模块以支出、收入、转账三种统一类型的流水为核心，提供记一笔、流水筛选分页、编辑、删除与 CSV 导出；账单导入模块实现支付宝、微信账单的「上传—预览—确认—入账」流程与批次撤销；统计报表模块提供首页仪表盘与分析页两组只读接口，向图表输送汇总数据。

接口层面，系统以 `{"code": 0, "message": "ok", "data": ...}` 作为统一返回格式：code 为 0 表示成功，非 0 携带业务错误信息，由全局异常处理器将业务异常、参数校验失败等统一转换，保证前端可以以一致的方式处理错误。全部 26 个 REST 接口按模块归纳见表 4.6。

## 4.4 关键业务流程设计

### 4.4.1 记账与余额联动

记账是系统最高频的写操作，其流程如图 4.3 所示。请求先经 Controller 完成与账户无关的静态校验（金额大于 0、转账两账户不同、账户未归档、账户归属当前用户），随后 Service 开启事务，插入交易记录，并按流水类型对相应账户执行余额联动——支出仅 from 账户减少、收入仅 to 账户增加、转账两者兼有。任一步失败则整体回滚。

**【插图】图 4.3 记账与余额联动流程图**（figures/fig4-3-record-flow.png）

编辑流水在同一套机制上采用「两步法」：事务内先将旧记录按其旧值反向冲销，再按新值重新入账并更新流水各字段。该方法天然支持更换账户、在三种类型之间互换等任意字段变更，且编辑后余额始终等于未删除流水影响之和，无需为「改账户」「改类型」单独设计对账逻辑。

### 4.4.2 账单导入

账单导入将「人工逐笔记账」压缩为「上传一次、确认一次」，其流程如图 4.4 所示。系统按平台选择对应的解析器（二者实现统一的 BillParser 接口）解析出标准化行后，依次完成清洗过滤、分类自动映射、入账账户匹配与重复检测四个纯内存步骤，生成预览返回前端——此阶段不落库，避免脏数据入库。用户在预览页修正分类与账户并勾选后提交，系统以单个事务完成批次插入、流水批量写入与逐条余额更新。

**【插图】图 4.4 账单导入流程图**（figures/fig4-4-import-flow.png）

### 4.4.3 批次撤销

批次撤销是导入的逆向操作，其流程如图 4.5 所示。撤销以批次状态机为约束：仅 confirmed 状态的批次可撤销，且状态转移通过条件更新（UPDATE … WHERE status = 'confirmed'）抢占完成，防止并发下的重复撤销。撤销在单事务内将批次内全部流水软删除、逐条反向冲销余额，并将批次置为 rolled_back。撤销后账户余额完整还原，原文件可重新导入。

**【插图】图 4.5 批次撤销流程图**（figures/fig4-5-rollback-flow.png）

余额校正的流程与上述机制同构：计算实际余额与当前余额的差额，差额为正记一笔收入、为负记一笔支出，分类归入「其他」，来源标记为 reconcile，复用与导入入账完全相同的流水生成与余额联动路径，不引入任何新的余额变更逻辑。

## 4.5 本章小结

本章完成了系统的总体设计：架构上采用前后端分离与四层结构，以 JWT 实现无状态鉴权；数据上以 5 张表承载全部业务，通过余额原子联动、负债负余额、软删除与对账校正四条规则保证账务一致性；流程上以统一的 from/to 模型和事务边界覆盖记账、导入、撤销与对账全部写路径。上述设计为下一章的系统实现提供了直接依据。
